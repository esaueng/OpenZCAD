OpenZCAD · file import

Is it working, or is it stuck?

Importing a 283 MB STEP assembly today produces one piece of feedback: the line “Rebuilding assembly.step with the exact geometry kernel…” in the status bar, and a blue dot. It never moves. For minutes.

This is the smallest thing that fixes it — one card, three lines, one control. No settings, no options, nothing to configure. It appears when an import will take a while, and it goes away.

Anatomy

Everything it shows, and nothing else

Frozen at the hardest moment: the kernel is chewing on the file and nothing can be measured.

assembly.step

Building geometry9.4 s

  1. 1

    The file name, and what it is doing right now

    Four phases, in plain words: saving to this device, reading the file, building geometry, archiving the original. No sub-steps, no counts, no checklist of what already finished.

  2. 2

    A clock that proves it is alive

    It runs on the main thread, so it keeps ticking even while the worker is frozen inside the kernel. This is the single most important element on the card — everything else could go and it would still answer the question.

  3. 3

    One bar that never lies

    It fills while progress is genuinely knowable. During the kernel call — one synchronous wasm call that cannot report anything — it stops moving and starts striping. A held, striped bar says “running, extent unknown”. A bar that creeps to 90% and sits there is a lie.

Why the bar behaves that way

Two of four phases are worth measuring

The long pole cannot be measured at all: kernel.importStep() is a single synchronous call into wasm that blocks the worker thread it runs on, so it can post neither a percentage nor a heartbeat. Reading the file turned out to be the opposite problem — measured, it is too fast to be worth a number.

PhaseSignalWhat the bar does
Saving to this device bytes Fills, over the streamed blob read. Measured on 250 MB: read ~0.12 s, SHA-256 ~0.2 s. The IndexedDB write that follows reports nothing, so the bar parks at the end of this phase for the length of that write.
Reading the file too fast Reports no fraction. Measured at about 0.15 s for 250 MB — decode and header scan together — so there is nothing to watch. It stays a named phase only because it is the truthful label for that moment.
Building geometry opaque Holds and stripes. The solid-checking and tessellation loops either side of the blocking call are countable, but showing those counts is detail this card does not need.
Archiving the original parts Fills. Exact — the 16 MB part plan is computed up front, so 283 MB is 18 known steps.

How it ends

Three endings

Each is one line. Only one of them earns a button, because only one of them leaves something for you to do.

Refusals that happen before anything starts — file over the 250 MB cap, browser storage unavailable, another exact operation still running — never get a card at all. They are settled in under a second, and the status line already handles them.

Built

Where it touches the code

The import already ran as an ordered sequence of exactly these phases — it just reported none of them. Every change is additive; the progress sink is optional on the run, because nothing it carries reaches the document or the device.

apps/web/src/lib/importProgress.ts

New. The phase vocabulary, the weights that divide the bar, the bar arithmetic, and the filter that keeps a four-thousand-chunk read from re-rendering the workspace four thousand times.

apps/web/src/lib/stepImportRun.ts

A progress sink beside the existing status sink, emitting one phase at each of the four steps its header comment already enumerates, plus one place that maps how a run ended to the line the card shows. No control-flow change.

apps/web/src/lib/localProjectStore.ts

Reads the blob through stream() with a byte callback instead of one arrayBuffer() call, then digests. Allocates the destination once at the blob's size, so peak memory matches the old path rather than doubling it. Falls back to arrayBuffer() whenever anything is unexpected.

apps/web/src/lib/artifactUpload.ts

An optional onProgress callback in uploadArtifactBody, reporting the byte the store has actually accepted after each part.

apps/web/src/components/ImportProgressCard.tsx

New, and small. Owns the elapsed clock and the 600 ms appearance threshold. The clock lives here rather than in the workspace: it ticks ten times a second, and state that ticked in App would re-render the editor around the viewport for the whole length of an import.

Not built: cancel. The ✕ hides the card and the import keeps running, which is what its label says. A real cancel would have to thread an abort through the source-blob settlement — the logic that decides whether up to 250 MB of stored bytes are kept or pruned — and the geometry worker supports no cancellation at all, so the phase you would most want to stop is the one phase that cannot be stopped. Worth doing, separately, on its own terms.

Two things noticed while measuring, unrelated to progress and worth their own change: file.text() pulls the whole file into a JS string purely to regex two entity types, doubling peak memory on a 250 MB import; and the per-solid rejection reasons the kernel collects are flattened into a single sentence before anyone sees them.
