# ADR-017: Client-generated artifact storage

## Status

Accepted.

## Decision

STEP and STL bytes are generated by the exact geometry adapter in the browser
worker. The Cloudflare Worker never rebuilds geometry: it authorizes a bounded
upload, writes the bytes to the private `ARTIFACTS` R2 bucket, and records the
finalized artifact metadata in D1.

Upload sessions expire after the application TTL. An hourly Worker cron scans
at most 100 expired sessions, deletes each referenced R2 object, and removes
only the D1 rows whose object deletion succeeded. Creating another upload also
runs the same bounded sweep. A failed R2 deletion therefore remains visible and
retryable rather than becoming an untracked object.

Permanent artifact deletion is likewise object-first: project purge deletes
every referenced R2 object before deleting D1 rows. If object deletion fails,
the database records and project remain for a later retry.

R2's default seven-day incomplete-multipart lifecycle remains a defense for
future multipart clients. The current browser flow uses one bounded `PUT`, so
the application sweep—not a broad object-expiration rule—is authoritative. A
bucket-wide or `projects/*` TTL must not be enabled because it would delete
finalized user artifacts as well as abandoned uploads.

## Consequences

- Export stays local-first: the file download succeeds even when archival is
  unavailable.
- D1 is the deletion manifest for R2, and cleanup never discards that manifest
  before the corresponding object deletion succeeds.
- The checked-in cron changes only the non-production Worker configuration;
  applying it still requires a separately approved deployment.
- The obsolete job, queue, workflow, and server-side geometry path remains
  absent.
