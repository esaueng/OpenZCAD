Phase 1d, the room merge in the browser ([PR #827](https://github.com/esaueng/OpenZCAD/pull/827)): the collaboration room orders versions and never merges; a submission that descends from an older room version it still holds is refused as a conflict carrying that `base`, and the submitting browser merges base, latest and its current document (edits made while the stale submission was in flight included) with `mergeCollaborationDocuments`, now in `@openzcad/document-core`, then resubmits on the latest version over the socket or, when oversize, over HTTP. A named save that is draining the stale edit waits for the merged resubmission. A merge that conflicts or fails validation, a base other than the one submitted on, or a fourth stale conflict in a row without an acknowledgement falls back to the manual conflict dialog; a pre-Phase 1 browser gets that dialog where the room used to merge for it. Evidence: `apps/web/src/lib/useCollaboration.test.tsx` (merge with and without in-flight edits, unmergeable edits, a foreign base, the retry cap, the HTTP path, base parsing), the draining case in `useCollaborationCheckpoint.test.tsx`, and the room-side cases in `test/cloudflare-adapters.test.ts`, `test/project-edit-lease.test.ts`, `test/collaboration-room-socket.test.ts`, `test/object-folders-collaboration.test.ts` and `test/mesh-artifact-discard.test.ts` (a late edit merged after a copy completion advanced the room).
