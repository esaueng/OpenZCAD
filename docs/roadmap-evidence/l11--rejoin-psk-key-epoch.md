Crypto context fix, no migration and no flag change: the `rejoin-psk` AES-KW wrap context is now `{userId, projectId, keyEpoch}` instead of `{userId, projectId, epoch}`. It bound the MLS group epoch, which restarts at 0 after an identity-authorized group reset (decision D9, slice 4-10), so two generations' rejoin PSKs of the same MLS epoch shared one context and a server could serve the replaced group's wrap as the new group's. The key epoch (decision D10) is the monotonic project-key generation the wrap is already stored and looked up by (`e2ee_project_keys.key_epoch`), so the context now names exactly the row; the PSK's MLS epoch is still `keyEpoch - keyEpochBase`. Every wrap and unwrap goes through `projectGroups.ts` (`wrapEpochKeys` for group creation, Commits and External Commit rejoins, invitations' own-key posts, device-removal rotations and resets; `newestRejoinPsk` for rejoins). No rejoin-PSK wrap is stored while `E2EE_PROJECTS_ENABLED` is off. Evidence: `packages/crypto/src/vectors.test.ts` (new fixed `rejoin-psk` vector), `packages/crypto/src/wrap.test.ts` (a wrap relabelled with another group generation's key epoch for the same MLS epoch does not open; the old `epoch` field is refused) and `test/e2ee-device-removal.test.ts` (after a reset the server serves the replaced group's MLS-epoch-0 rejoin wrap as the new group's: the rejoin fails with `authentication-failed`, and before this change it succeeded; the genuine wrap rejoins; the rotated wraps open under the new account key with the key-epoch context and not under the removed device's).
