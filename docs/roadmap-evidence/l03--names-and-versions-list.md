Slice 1, save-point names and the versions list (plan: docs/plans/l08-l03-review-and-versions-plan.md). A save point can be renamed after it is made (Revisions › open a row › Rename; Escape keeps the name). The new `name` shows in place of the reason it was saved with, which stays in the row's details ("Saved as …"); an empty name, or the reason itself, clears it. A rename is a forward document write (a "Rename save point" revision, version advanced, no undo entry, since undo never rewinds the save-point list), so it syncs like any edit and needs edit rights. Each save point now records its author (`userId`, display name, and a device name such as "Chrome on macOS"), and every row shows three columns: editor ("You" for the signed-in account's own saves), device, and where the save's model is stored (this device, the account, both, or not stored). Both fields are optional and additive: older save points show only the storage column, older clients keep the fields through normalization (no schema version), and a malformed name or author is dropped without losing the save point. E2EE: the fields live inside the project document, which an encrypted project keeps encrypted and signed (ADR-024), and share-link snapshots carry no save points, so the server and link visitors learn nothing new. Evidence: `test/checkpoint-versions.test.ts` (author on all four save-point constructors, bounds, rename/clear/no-op, rename kept through undo, normalization and the account's save-point check), `RevisionsPanel.test.tsx`, `checkpointAuthor.test.ts`, and the CI smoke case `test/e2e/save-state-versions.spec.ts` (save, the three columns, rename, details, reload).
