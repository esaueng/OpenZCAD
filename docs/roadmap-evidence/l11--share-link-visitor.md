Phase 5, slice 5-11, the visitor page of share links to end-to-end encrypted projects, behind the same flags as slice 5-10 (`E2EE_PROJECTS_ENABLED` and the sharing rollout), with no new migration. The app reads `#share=<token>.<key>.<owner>` as an encrypted link (`shareLinkFromHash`, `isEncryptedShareLink` in `projectShareLink.ts`) and every plaintext `#share=<token>` exactly as before (same parser, route, session, Tweak workspace and device copy). An encrypted link is opened by `sharedSnapshotLoader.ts`, loaded only then: the anonymous `GET /api/e2ee/share/:token` (a 404 reads as "no longer available", as for plaintext links), `openSharedSnapshot` in the ADR's order (owner hash, delegation and expiry, delegated signer, statement and expiry, named author, snapshot signature and project), the share-version key opened with the share key and the snapshot decrypted in the decode worker (no MLS), then every file the document uses (imports and pictures) fetched from the new anonymous `GET /api/e2ee/share/:token/blobs/:blobId`, decrypted in the decode worker against the snapshot body's reference and checked against the document's checksum before it reaches the device source store; nothing opens until all have. Refusals are plain words by reason: an expired statement or delegation reads "The owner hasn't recently confirmed this link…", one from the future asks to check the device clock, a wrong key or owner in the fragment says the link is incomplete or changed, a forged snapshot or a file that does not match says it could not be verified. The workspace follows the verified statement's mode, never the server's: a view-only link pins View (Tweak locked, Make a copy on View's rail), a tweak link lands in Tweak as plaintext links do. Make a copy for a signed-in visitor of an encrypted link asks where (`SharedLinkCopyDialog`): into the account, saved as any device project is (slice 4-8's adoption: encrypted under the visitor's keys when the account encrypts new projects, decision D2, and an ordinary project otherwise, which the dialog says), or on this device only; signed-out visitors and plaintext links keep the device copy. The blob route goes through every gate of the snapshot route (format 2, not trashed, link live with a statement and snapshot, the owner's sharing switch, the 0040 and content-blob tables) and serves the owner's ciphertext only for a committed blob of the link's project that the stored snapshot's header names, else one opaque 404. Both anonymous encrypted routes are rate limited per client address with the existing public pattern (`enforceApiRateLimit` over `publicRequestBucket`; 60 snapshot and 300 blob reads a minute) once the flags serve them, and not at all while they are off; plaintext share routes are untouched. Evidence: `test/e2ee-share-link-visitor.test.ts` (the real Worker over SQLite with slice 5-10's Node devices: view and tweak links opened with the statement's mode even when the server claims another, the STEP file arriving through the blob route; a revoked link answering null and its blobs 404; expired statements and delegations refused as not recently confirmed, a future one as the clock; a wrong key or owner in the fragment, a forged snapshot, altered blob ciphertext and a swapped blob refused with nothing stored; the blob route refusing unnamed blobs, other links' tokens, malformed paths, flags and the owner's switch off; rate limits per address with plaintext links unlimited; Make a copy into an opted-in account, encrypted, its file a new blob of the copy that a reloaded device decrypts, and into another account as an ordinary project), `test/project-share-link.test.ts`, `SharedLinkCopyDialog.test.tsx`, and Playwright `encrypted-share-links.spec.ts` (the owner imports a STEP file into an encrypted project and creates a link from the dialog; a signed-out visitor in a fresh context opens it, the model rebuilds from the decrypted blob, View is pinned and only the anonymous encrypted routes are requested; a device copy opens Build; a visitor eight days ahead sees "The owner hasn't recently confirmed this link"; after the owner revokes it, the visitor sees the refusal), with `encrypted-share-links-owner.spec.ts` moved onto the shared `encrypted-share-links-fixtures.ts`.
