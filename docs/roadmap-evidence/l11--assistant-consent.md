Phase 6, slice 6-1, per-project assistant consent on encrypted projects (plan default M6: per user, per project), lifting decision D7 one project at a time. The consent copy lists everything an assistant request sends (`apps/web/src/lib/assistant/consentCopy.ts`): the prompt, up to 12 earlier conversation turns, the model digest (project id, name, units, version, schema version, parameters, every feature's full definition including sketch text, bodies with volumes, bounding boxes and measured faces and edges, the measured edit catalog, warnings) and the selection, attached images and drawing pages with their file names, the client's operation list and a retry flag; it names the provider route (the user's own key, or the deployment's provider and model, and the endpoint's host), says that OpenZCAD's server reads the request in plaintext to pass it on with its own instructions, any custom instructions and an account-derived identifier, and that what was sent cannot be recalled. `ASSISTANT_CONSENT_COPY_VERSION` (1) is pinned to the exact request and digest field lists by tests, including a compile-time map of `CadDocumentDigest`'s keys. The record `{userId, projectId, allowed, copyVersion, route, sequence}` is canonical JSON MAC'd with HMAC-SHA-256 under an HKDF of the account key with its own label (`OpenZCAD E2EE v1 assistant consent mac`, fixed vector in `packages/crypto/src/assistant-consent.test.ts`); browsers pin the sequence per project and send only on a record that verifies, is not below the pin, allows the project and names the current copy and route, re-reading it before every request, so a server-forged consent never makes a browser send. Migration `0041_e2ee_assistant_consents.sql` stores one row per user and project (erasure fences, forward-only sequence, removed by profile erasure and project purge); `/api/e2ee/assistant-consents` (behind `E2EE_PROJECTS_ENABLED`, 503 before 0041) lists, reads and stores the caller's records for encrypted projects it owns or belongs to, and `…/:projectId/members` shows co-members who allowed it. The Worker's assistant gate admits a format-2 project only with a live row for that user, current copy and the route the request would take (409 `ENCRYPTED_PROJECT_ASSISTANT_CONSENT_REQUIRED`); without the flag or 0041 it refuses as before, and plaintext requests are unchanged. UI: a consent dialog on first use, an "Allowed for this project" chip with Stop in the assistant panel (Stop aborts the request in flight and writes the next sequence with `allowed = false`, which marks the Worker row revoked), an Assistant row in the project properties, and Settings › Encryption › "Assistant access" with Revoke; consent is asked again after a revocation or a copy, key source, provider, model or endpoint change (the route carries a SHA-256 digest of all four in full, so no two routes collide). ADR-024's assistant section now lists the full payload. Evidence: `packages/crypto/src/assistant-consent.test.ts`, `test/e2ee-assistant-consent.test.ts` (refusal without consent, after revocation, for another user, for another route and after the upstream endpoint changes; migration-missing and flag-off cases with plaintext requests reaching the provider unchanged; erasure and purge), `apps/web/src/components/assistant/AssistantPanel.consent.test.tsx`, `apps/web/src/components/assistant/AssistantPanel.encrypted.test.tsx`, `apps/web/src/lib/assistant/consentCopy.test.ts` (route collisions), `apps/web/src/components/assistant/AssistantConsentDialog.test.tsx` (no decline while an allow is stored), `packages/shared/src/sha256-sync.test.ts`, `apps/web/src/components/AssistantAccessSettings.test.tsx` and `test/e2e/encrypted-assistant-consent.spec.ts` (the intercepted request carries exactly the listed fields, and nothing is sent after Stop or Revoke).
