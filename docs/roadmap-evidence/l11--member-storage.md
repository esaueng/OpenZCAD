Phase 5, slice 5-2, member-aware storage for end-to-end encrypted projects, with no migration. The Worker's encrypted routes replace the owner-only check and `PROJECT_FENCE` with role-aware access from `project_members` (`requireEncryptedProjectAccess`, and `MEMBER_FENCE` and `WRITER_FENCE` inside every write statement). Any member reads documents, versions, revisions, project info, content blobs, measurements, view state, the MLS group, key archives, leaves and resets. Only the owner reads a project in the recycle bin. The owner and editors write document versions (account and room), revisions, project info, content blobs (counted against the owner's artifact storage) and measurements, and a viewer's write is refused with 403 `E2EE_PROJECT_READ_ONLY`. Any member keeps its own view state, as plaintext workspace sessions allow, and any member sends MLS Commits, since every member's browser runs the policy that decides what a Commit may do. Group creation and resets stay owner-only. Any member copies a project it reads, into a project of its own. `POST /api/e2ee/projects/:id/keys` stores the caller's own account-wrapped project key and rejoin PSK for an epoch of the current group, posted by a certified device and never replacing a stored wrap. `GET …/keys` still serves only the caller's own wraps. `GET /api/e2ee/projects/:id/revocation-cutoffs` serves the other members' identity-signed cutoff statements to members. On format-2 projects the plaintext member `PATCH` and `DELETE` (`/members/:id`) move from metadata to refused as sharing (`ENCRYPTED_PROJECT_SHARING_UNAVAILABLE`), since a role changes only by a Commit; plaintext projects are unchanged. In the browser, `projectGroups.ts` takes the co-members' verified device lists (`ProjectGroupContext.members`, which contacts and pins supply from slice 5-1; without it a project stays solo and another account's leaf is refused as before). With them, the MLS directory, key archives and authorship accept co-members' devices with their own verified revocation cutoffs. A device that processes someone else's Commit posts its account's own wraps of the new epoch (`postOwnEpochKeys`). `epochRoles` reads the roles extension from each epoch's archived GroupContext (`mls/epochRoles.ts`, a strict TLS parser checked against the engine), or from the device's own session for the epoch it holds. The store's `requireAuthority`, the version log check, and the check of project info and measurements written by co-members now require the role the author held in the version's own epoch. They no longer pass an author with no role entry, and they keep a demoted editor's earlier versions valid. A viewer's own browser refuses to send a write. Evidence: `test/e2ee-member-storage.test.ts` (Node devices of two accounts and an outsider; a member is added by the owner's `setRoles` Commit and joins by External Commit with a rejoin PSK it posts as its own, standing in for slice 5-3's Welcome): a member reads and an editor writes a version, project info, measurements and a file that the owner's fresh browser verifies, the owner posts its own wraps on processing the member's Commit, and a solo-configured browser refuses the member's leaf; a viewer's write is refused by its own browser, by the Worker (versions, blobs, measurements) and, when a lying server lets it in, by every browser; a demoted editor's version still verifies while the demoted browser stops writing; a removed member's later version is refused by an honest Worker and, served anyway, by every browser; the wrap route serves and stores only the caller's own wraps, keeps stored ones and refuses unknown epochs, foreign devices and outsiders; the cutoff route serves other members' statements to members only; an author with no role entry is refused even with a leaf. Also covered by `apps/web/src/lib/e2ee/mls/epochRoles.test.ts` and the updated access cases in `test/e2ee-project-documents.test.ts`, `test/e2ee-project-groups.test.ts` and `test/e2ee-project-format.test.ts`. The flags stay off.
