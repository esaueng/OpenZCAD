Phase 3, Keychain cleanup (the four findings deferred on #842): no flow leaves an unreachable Keychain key. Every device creation path (setup, enrollment, approval) goes through one candidate wrapper, `withNewDevice` in `accountKeys.ts`, which discards the new keys through the store's `discardCandidate` when the flow stops before the store write (the settings close or the session changes while the Keychain is creating or importing them); from the write on, `keychainDeviceStore` keeps a candidate's keys only if its stored record holds them, whether the write resolved or rejected, so a rejected IndexedDB `getOrCreateDevice`, compare-and-swap or save removes them too. A confirmed erasure that signs out also removes the device record and its Keychain keys, keys first, so a refused native removal keeps the record and key id for the account's next removal (user ids are stable per email). `openzcad-device-keys::create` returns a `CreateError` whose `key_id` names a signing key it stored but could not remove after a failed unlock-key write; the `create_device_keys` command passes it to the renderer as `NativeDeviceKeysError.keyId`, which retries the removal at once and before each later creation. Evidence: `test/e2ee-account-keys.test.ts` ("desktop Keychain device keys": session ending during setup, enrollment and approval key creation; a rejected IndexedDB setup write; erasure removing the device and native keys, and a refused removal retried), `apps/web/src/lib/e2ee/keychainDeviceKeys.test.ts` (rejected writes, `discardCandidate`, leftover retry), `apps/web/src/lib/desktopBridge.test.ts`, and the crate tests for the double failure. The Keychain calls themselves run only on macOS; the manual Apple Silicon workflow was not dispatched.
