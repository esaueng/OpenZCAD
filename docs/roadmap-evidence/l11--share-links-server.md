Phase 5, slice 5-10, share links of end-to-end encrypted projects, server and owner flow, behind the same flags as slices 5-2 to 5-5 (`E2EE_KEYS_ENABLED`, `E2EE_PROJECTS_ENABLED`, the sharing rollout), with migration 0040 `e2ee_share_links` (links with their token hash, mode, share key hash, owner fingerprint and newest share-authority statement; `e2ee_share_keys`, the share key wrapped per key epoch; `e2ee_share_snapshots`, the current snapshot per link, inline or in R2; `e2ee_share_delegations`, each account's newest identity-signed delegation). A link is `#share=<token>.<key>.<owner>` (base64url of 32 bytes each; the token is a labelled hash of the share key and the server keeps only the token's hash; `shareLinkFragment.ts`). The owner creates a link by an owner-signed grant at the current key epoch in a new version whose body carries the set (body version 2), then registers it with the share key wrapped under that epoch's project key, a statement and the first snapshot (`createShareLink` in `shareLinks.ts`); revoking signs a permanent tombstone in place of the grant in a new version, after which `DELETE …/share-links/:shareId` drops the snapshot, key wraps and statement at once and keeps the row so the id and token are never reused. The tombstone, not that one request, decides: while the server still lists a link the head tombstones, the owner's browser sends the `DELETE` again (`forgetRevokedShareLinks`) on the next revoke, whenever the sharing dialog loads the links and after a removal, revoking an already tombstoned link only re-sends it, and the dialog keeps the link listed as "Revocation pending" with the error until the server confirms (tested in `test/e2ee-share-links.test.ts` and `EncryptedShareLinks.test.tsx` with a forget that fails after the tombstone committed). Statements last at most seven days with a sequence that rises per link (the Worker refuses anything else), name the signing keys of the owner's and every current editor's devices from the pinned device lists, and are reissued when missing, within two days of expiry, when the author set changed (an editor removed, a device revoked or added) or when their signer left the delegation, and at once after a removal through slice 5-5's `onMembersRemoved` (`shareLinksAfterRemoval`). The delegation (identity key; 30 days, the owner's certified devices) is renewed with a passkey or the recovery key from the sharing dialog when missing, stale or in its last week, and at once on an owner device removal with the identity key the removal opened (`renewShareDelegationAfterRemoval`, `pageDeviceRemoval.ts`). Every saving editor republishes one share-snapshot envelope per active link of the head's set: the shared projection in a version 1 body, a fresh version key wrapped under the project and share keys (`wrapShareSnapshotKey`, `versionId` the decimal document version), signed by its device, under the current key epoch (the share key is wrapped again for it first). Every head the store accepts, from the account or the room, runs `verifyShareLinkSet` against the parent's verified set (the full rule for a direct parent, tombstones only across skipped versions), `authorIsOwner` from the epoch's roles and the tombstones this browser saw, which the version pins persist (`shareLinkSet.ts`; integrity reason `share-links`); writes carry the set unchanged, and a page save naming the head a share-link version replaced lands on top of it. When a link names an earlier owner identity every link is tombstoned and reissue is offered (`maintainShareLinks`). The anonymous `GET /api/e2ee/share/:token` serves the snapshot envelope with its signature, the visitor's wrap, the author's key, the statement, the owner's delegation and identity key, only for format-2 projects that are not trashed, while the owner's sharing switch and the deployment's flags are on (one opaque 404 otherwise); the plaintext `#share=<token>` route and its links are untouched and keep refusing format 2. The sharing dialog's encrypted branch mounts `EncryptedShareLinks` for the owner: create, copy, revoke, "Active until …" or "Needs confirming", Confirm sharing, and reissue after a removal or an identity change. Without migration 0040 the share-link routes answer 503, the anonymous route 404, and encrypted writes, plaintext links, erasure and purge work as before; purge deletes the rows and R2 bodies, erasure deletes the delegation and, with `all`, clears user ids. Evidence: `test/e2ee-share-links.test.ts` (Node devices, the in-process MLS engine and the real Worker over SQLite: a link created, read anonymously and verified end to end with `verifySharedSnapshot`, ciphertext only and no plaintext route; a stale page save landing on the share-link version; owner-only routes, rising sequences, stale epochs and viewers refused; a revocation removing the snapshot, the editor's browser remembering the tombstone, and a hostile editor's version re-listing the grant refused by the owner's page and by a reloaded one; an editor dropping a link refused; an editor's save republishing two links under its own key; removing an editor issuing a statement without its devices, its snapshot refused until the owner republishes, and reissue; an editor's revoked device dropping out; no delegation leaving the link unstated, expiry of statements and delegations, and a delegation of uncertified devices refused; an owner device removal renewing the delegation; forged and stale snapshots, statements, owner keys and wraps refused by the visitor; an identity change retiring and reissuing links; migration 0040 missing; erasure and purge), `EncryptedShareLinks.test.tsx`, `ProjectSharingDialog.test.tsx`, and Playwright `encrypted-share-links-owner.spec.ts` (the owner confirms sharing with the recovery key, creates a link from the dialog, the anonymous route serves a snapshot that verifies and decrypts, revocation leaves a 404, and autosave keeps working). Since the first share-key wrap per key epoch wins, `POST …/share-links/:shareId/keys` takes one only signed (`signShareKeyWrap`, "OZW") by a device the caller's newest device list certifies and fences the insert on that list's head, so a revoked device of an account that stays an editor cannot plant a wrap no member can open, and a member's browser takes the newest wrap that opens to the grant's key rather than failing on one that does not (tested in `test/e2ee-share-links.test.ts`, share-key wraps). Forgetting a link is permanent, so `DELETE …/share-links/:shareId` also needs, besides the owner account, a signature (`signShareLinkForget`, "OZF") over the project, the link and the current key epoch by a device the owner's newest device list certifies, fenced on that list's head, so an owner device removed while its session stays signed in cannot forget the links (tested in `test/e2ee-share-links.test.ts`, forgetting a link: a removed owner device refused, a signature for another link or epoch refused, a device-list change in the batch changing nothing).
