Phase 7, slice 7-3, the beta-only reverse path that turns an encrypted project back into plaintext, behind the new off-by-default `E2EE_REVERSE_ENABLED` (open only to accounts migration is open to, so it also needs `E2EE_MIGRATION_ENABLED` and encrypted projects; reported in `/api/e2ee/config` as `reverseEnabled` only once open and migration 0043 is installed; Phase 8 deletes it). It reuses migration 0042's state machine with direction `decrypt`; D1 migration `0043_e2ee_reverse_staging.sql` adds no table, only the view `e2ee_decrypt_staged_projects` (format-2 projects with a decrypt row `staging` or `abandoned`) and replaces migration 0022's artifact, document-object and storage-asset quota triggers, migration 0017's finalized-usage counters and migration 0042's version quota so the plaintext staged beside an encrypted project counts toward nothing until the cutover (mirroring decision M10; before any decrypt row the view is empty and every answer is unchanged). The start (`apps/web/worker/e2eeProjectMigrations.ts`) refuses unless the caller owns a live format-2 project with no members, pending invitations, live share links or (when migration 0038 is installed) pending encrypted invitations, and the account's "Encrypt new projects" opt-in is off (decision D2, 409 `E2EE_MIGRATION_OPTED_IN`), all fenced again in the insert; it locks the encrypted room. While staging, encrypted content writes (documents, versions, revisions, project info, measurements, view state, blobs; MLS key management keeps working) and the room answer 409 `PROJECT_MIGRATING` (`e2ee.ts`, `projectFormatGate.ts`), and the owner's lease holder writes the decrypted plaintext under the same project id through the ordinary plaintext routes naming the lease (`apps/web/worker/e2eeReverseStaging.ts`): save states (`POST …/revisions`, under their own revision ids) and the head (`PUT …/document`, recorded on the migration row by version and checksum) through `D1R2PersistenceService.stageDecryptedDocument`, files through the plaintext upload sessions and finalize, each fenced on the lease in its own SQL and never touching the project row; measurements and view state through `PUT …/migration/plaintext/details`; `GET …/migration/plaintext` is the journal. The cutover is one batch: every retained encrypted save state has a staged plaintext save state, the staged head is newer than the encrypted head, which (with the encrypted measurements) did not move, still unshared and not opted in; it flips `storage_format` to 1 at the staged head and moves the owner's artifact usage from the blobs' ciphertext to the staged files. The purge clears the room's encrypted ledger (a `format: 2` room migration request) and then drops groups, leaves, Commits, wraps, archives, resets, versions and their R2 bodies, envelopes, blobs and their R2 objects a bounded step at a time, through the cleanup an abandoned encrypt staging uses; an abandon drops the staged plaintext rows and objects the same way, and the hourly sweep finishes either. The cutover also refuses, with 413 `ARTIFACT_QUOTA_EXCEEDED` or `PROJECT_STORAGE_QUOTA` in the same statement that ends the staging exemption (non-retryable in the engine; the project stays encrypted and can be abandoned), when the owner's artifact usage or project storage after it would exceed their limit, a further staged upload is refused early once that limit is already reached, and a resumed staging reuses a journaled head of the same version and checksum while the purge's last step drops any staged head the cutover left unreferenced (both covered in `test/e2ee-project-migration-reverse.test.ts`). Project deletion now drops the migration row last, so a deleted mid-staging project's exempt files never leave usage behind. In the browser, `apps/web/src/lib/e2ee/projectDecryptionEngine.ts` reads through the verifying encrypted store, decrypts every blob a save state or the head names into an ordinary file (STEP archive, mesh payload, reference picture, thumbnail, archived exports) named in its metadata by its blob id, rewrites the documents to the files' artifact ids, stages oldest first, the head at `sourceVersion + 1` under the project info's name, then measurements and view state, cuts over (forgetting the encrypted head, pins and keys) and purges; it resumes from the journal, restarts on a moved head and holds the encrypting runner's Web Lock (`projectDecryption.ts`). Settings › Encryption › "Stop encrypting a project" (`StopProjectEncryption.tsx`) appears only when the flag is on, says plainly that the project's content will be stored readable by the server again, and asks for a confirmation per project.
