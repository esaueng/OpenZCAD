Phase 8, slice 8-C1 (no migration): share-link server hardening. Each R2 snapshot object is keyed by its link and write; replacement reads the previous object key inside its own batch and deletes only that object. Forgetting retains the snapshot row until R2 deletion succeeds and retries leftovers. Snapshot and delegation writes carry the signer's device-list fence. Link registration needs a certified owner's device signature (`signShareLinkRegistration`, OZN), fenced on the device list and live-link limit. Anonymous blob reads retain a snapshot-sized per-address/link allowance, with a spent marker checked before snapshot access and the address's independent fallback budget. Snapshot authorization uses only the header's blob ids, cached per isolate or fetched through ranged prefix reads capped at 60 per address per minute across links. Evidence: `test/e2ee-share-links.test.ts`, `test/e2ee-share-link-visitor.test.ts` and `packages/crypto/src/share-links.test.ts` cover cross-link object reuse, replacement races, failed-delete recovery, device-list changes, registration signatures, a 400-blob load without snapshot body reads and refusal before further R2 reads once both budgets are spent.

Review follow-up: anonymous downloads of one project blob are limited to four per address per minute across every share link to that project, independently of the snapshot-sized load allowance and its address-budget fallback. The guard uses an opaque project/blob hash and runs before snapshot or content R2 reads. `test/e2ee-share-link-visitor.test.ts` covers a 4,096-blob allowance, repeated refusals with no storage reads, sibling links, distinct blobs, address isolation, minute reset, fallback and no extra counters after address exhaustion; the 400-blob load remains covered.
