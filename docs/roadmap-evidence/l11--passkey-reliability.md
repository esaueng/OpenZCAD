Passkey reliability across browsers and providers (ADR-024 amendment 2026-11-25): a new passkey that turns out to lack PRF is signalled away through the WebAuthn Signal API (`signalUnknownCredential`) while its id is still in memory, with the advice still naming the passkey (conditionally after a signal, since a provider may ignore it), and never for a credential that might have been certified. PRF results are read in every shape browsers and extensions return (Chrome `enabled: false`, Firefox `{}`, Safari's enabled-without-result, 1Password's 32-entry Array, every slot checked so a sparse array is refused), credentials are validated by shape so password-manager extensions work, prompts get five minutes for phone (QR) and Windows Hello ceremonies, `InvalidStateError`, `NotSupportedError`, `SecurityError` and `ConstraintError` each get an actionable message, and a missing PRF names the likely platform cause (older Windows Hello, Safari's QR flow, Firefox on Linux). The browser × OS × provider matrix in `docs/qa/passkey-compatibility.md` is from secondary sources and awaits real-device confirmation with its manual QA script. Regression evidence: `test/e2ee-passkeys.test.ts`, `test/e2ee-passkey-platform.test.ts`, `test/e2e/encryption-passkeys.spec.ts` (virtual authenticator without PRF, with and without the Signal API).
