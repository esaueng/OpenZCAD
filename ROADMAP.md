## Where we are

OpenZCAD has a working browser CAD foundation: exact solid modeling, editable
feature history, expressions, direct manipulation, local persistence, optional
cloud sync and collaboration. The largest remaining product gaps are complete
sketch constraint workflows, reference geometry, drawings and assemblies.
Recent work improved existing modeling and the bounded imported-holder workflow,
and the 14 September kernel-adoption wave (#330–#342) moved booleans, patterns,
blends, mesh import, sketch modify tools and sections onto typed kernel entry
points; it did not complete those larger milestones.
The 26 September comparison with a mainstream direct-modeling CAD confirmed
those four gaps and added a fifth that needs no kernel work: the workspace
conventions every mainstream tool shares (a full hotkey set, saved views, item
groups, history step actions, notable-point measurement picks, X-ray display). It also
recorded that the reference CAD ships drawings, visualization and share links
with no assemblies at all, which supports the milestone order below.
The FreeCAD walkthrough reinforces the same sequence: actionable sketch feedback,
coherent expression/feature editing and a dimensioned drawing handoff, then
component instances and grounding before joint solving. Keep the quiet-stage
workspace; breadth of a reference CAD is not a reason to copy its toolbar density.

**Status vocabulary:** `Open` means a defined remainder; `Partial` means a
bounded subset is delivered; `Revalidate` means the older finding lacks current
proof and must be reproduced before implementation; `Deferred` means deliberately
outside the next delivery sequence. No feature row below is claimed actively
owned without a linked open implementation PR. “Delivered” means merged source
with referenced evidence; production acceptance is recorded separately.

## Delivery order

Finish useful workflows before adding a second way to do the same action.
Use the ordered product milestones below; kernel/reliability work runs alongside
only where dependencies and touched files are disjoint. Each row is an outcome,
not necessarily one PR. Split a large row into named, bounded slices under the
same ID before coding; never treat a partial slice as the whole row's completion.

| Order | Milestone                            | Exit signal                                                                                                                                                                                                                                              |
| ----- | ------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 0     | Close the shipped workflow gaps      | H01 has an explicit acceptance matrix; H02 has measured cold/warm behavior; U01/U02 resolve reproduced command/value/feedback disagreements; L01 records outstanding live checks.                                                                        |
| 1     | Complete the modeling foundation     | S01–S08, R01, F01–F05 and U05–U07 meet their row contracts: durable dimensions, understandable constraints, editable sketch geometry, useful reference/parameter surfaces, and the keyboard, history/items and viewing conventions of a mainstream tool. |
| 2     | Deepen part modeling and inspection  | Selected M01–M13, I01, I04–I08 slices work through creation, revision and export with their kernel prerequisites proved.                                                                                                                                 |
| 3     | Drawings MVP                         | D01 then a bounded D02 slice: aligned scaled views plus a useful dimension, explicit revision update/invalidation, offline reopen and PDF handoff. D03/D04 add sections and DXF; the milestone is a dimensioned shop handoff, not outlines alone.        |
| 4     | Assemblies MVP                       | AS01 then AS02/AS03; AS04/AS05 follow only when their query, exchange and reference dependencies qualify.                                                                                                                                                |
| Later | Reach, automation and new body types | Select L02–L09, D05, K09, M12 or I09–I20 from a measured use case; do not expand every lane at once.                                                                                                                                                     |

**Next bounded picks, in order:** [H02](#h02) remaining sustained publication-equivalence, branch lifetime, quiet target-device
timing and whole-worker retention evidence; [H01](#h01) remaining live
acceptance from its matrix; [S03](#s03) actionable constraint feedback;
[S02](#s02) the designed reference-dimension slice; [S04](#s04) composite-identity
implementation against its existing design; then [R01](#r01) the designed offset
datum-plane slice, [U05](#u05) keyboard/command coherence and [U06](#u06) history,
items and dependency inspection. [S01](#s01) saved driving-label placement is
complete and is not a future pick. U01/U02, the F05 expression audit and L01 can
proceed independently when ownership permits. Live acceptance needing
credentials/source data stays pending without blocking independent foundation
work. Check current row evidence and open implementation PRs before assigning a
slice; this sequence replaces the conflicting next lists in older plans.

These milestones are not a global gate: independent foundation work can run
while live acceptance is pending, and drawing/assembly design can start before
every part-modeling row is complete. No calendar estimates are carried forward
from audits of earlier interfaces.

## File interoperability

This lane has its own bounded sequence within the delivery milestones above:
complete [D04](#d04) DXF sketch exchange, [I07](#i07) SVG and [I06](#i06)
IGES, alongside [I02](#i02) STEP fidelity. Qualify [I10](#i10) before selecting
native-CAD implementations; the first package is [I11](#i11) Parasolid,
[I12](#i12) ACIS, [I13](#i13) Rhino and [I14](#i14) SolidWorks part import.
Inventor/JT follow demonstrated demand; Creo/NX/CATIA/Solid Edge are retained
as later targets. [I08](#i08) PLY export is a small independent slice; PDF
remains [D01](#d01), and [I09](#i09) USDZ is deferred visualization work.

Import means qualified geometry and supported metadata, not recovered source
feature history. Per-format direction/version claims require fixtures; native
assembly references must resolve explicitly, and mesh-only input cannot become
an exact solid merely by translation. Details and source evidence live in the
[format specification](docs/plans/file-format-interoperability.md); this table
is the only delivery-status ledger. Existing I04 owns export controls; I07 owns
SVG geometry, replacing the previously unnamed SVG slice in D04/I04.

## Completion and maintenance rules

1. Refresh main, the pinned kernel and open PR ownership before selecting a
   master ID. Use a new isolated branch; one bounded slice and one ready PR.
   A stacked PR names its dependency. Do not silently switch items when blocked:
   record the missing evidence/input against the selected row.
2. Before coding, record the slice, observable acceptance cases, dependencies
   and any schema/API/rollout decision. Preserve exactness/provenance, units,
   verified topology references, offline persistence and one-transaction undo.
   AI and manual edits use the same validated command path. Never weaken a
   refusal, oracle or tolerance to mark progress.
3. Run the root [AGENTS.md](AGENTS.md) verification gates and the row's browser,
   geometry or performance checks. Exact-head hosted checks are required before
   a merge decision; queued/skipped jobs are not passing. Deployment and manual
   Apple Silicon execution retain their separate authorization requirements.
4. Update this file in the implementation PR: status, shipped subset, evidence
   (tests plus PR/commit), remaining acceptance and changed dependencies. Add a
   linked child ID for a split, never a second untracked plan. Keep detailed
   acceptance specifications linked; do not copy their status tables back here
   as multiple competing versions.
5. Close only the scope proved. Move completed rows into the delivered baseline
   with their stable IDs, or retain a short completion row so links survive.
   Record live acceptance separately from merged source. Revalidate old kernel
   claims upstream and old UI findings on the rendered current app before work.
